# ADR-0020: Decide / Generate / Commit Split and the Focused Pulse

**Status**: Accepted and implemented (Phase 2 lane L3, 2026-11-06), as amended after the Phase 1 latency spike (`spike/RESULTS.md` on branch `spike/pulse-latency`). Implements D17 as changed by D52 and the addressed-reply targets. Decisions **D-71..D-75**.

## Context

`PulseScheduler.executePulse` ([`pulse-scheduler.ts:203`](../../packages/server/src/simulation/pulse-scheduler.ts)) walks the agents one at a time in a seeded order ([`:255`](../../packages/server/src/simulation/pulse-scheduler.ts)) and, inside each iteration, runs the pure engine step, commits engine events, awaits the LLM call ([`:354`](../../packages/server/src/simulation/pulse-scheduler.ts)), resolves and commits the intent, and persists state ([`:462`](../../packages/server/src/simulation/pulse-scheduler.ts)). Four properties make the hotel's latency targets unreachable as built:

- LLM calls are strictly sequential. Twelve agents with three consulted means three round trips in a row before the next pulse can start.
- `runPulse()` returns the in-flight promise when one exists ([`:173`](../../packages/server/src/simulation/pulse-scheduler.ts)). A human line that arrives mid-pulse cannot trigger a pulse of its own; it waits for the next scheduled one.
- Every pulse advances the clock by the configured interval (`simTime += pulseIntervalMs`, [`:204`](../../packages/server/src/simulation/pulse-scheduler.ts); `dt` from the same value at [`:206`](../../packages/server/src/simulation/pulse-scheduler.ts)) and increments `pulseIndex` at the end ([`finishPulse`, :573-577](../../packages/server/src/simulation/pulse-scheduler.ts)). An extra pulse would age emotions, refractories, stagnation and goal reviews a full interval for no wall time.
- Later agents in a pulse react to earlier agents' same-pulse commits only through `worldSignals`, built from the refreshed `newEvents` ([`:258-275`](../../packages/server/src/simulation/pulse-scheduler.ts), [`world-signals-builder.ts:36-50`](../../packages/server/src/simulation/world-signals-builder.ts)); the rolling context window is fixed at pulse start ([`:230`](../../packages/server/src/simulation/pulse-scheduler.ts)). That is the existing dog-pile damper, and a concurrent design weakens it.

## Decision

1. **Three phases inside one pulse (D-71).** (A) *Decide*, sequential in turn order: build the snapshot, `runEngineStep`, commit engine events, record `needsLLM` (ADR-0015 keeps the decision as its only owner). (B) *Generate*: for every agent with `needsLLM`, call `agentRuntime.generateIntent` with bounded concurrency (`generateConcurrency`, default **3** in the hotel, instance-wide across lanes) and one slot reserved for addressed replies. (C) *Commit*: resolve, append, project, apply memory, persist, **per task as its generate call settles** (live mode). Turn-ordered commit remains as `commitOrder: "turn"` (name illustrative) for eval and replay, where determinism matters more than latency. The mode is opt-in (`pulseMode: "split"`); the default `"sequential"` keeps today's loop byte-identical, so eval, the CLI and the web builder do not move.
2. **`runPulse` takes options (D-72).** `runPulse(opts?: { reason: "base" | "human_chat" | "body_arrived" | "wake"; focusAgentIds?: string[]; elapsedMs?: number })`. A focused pulse evaluates only `focusAgentIds` (turn order filtered), uses `dt = elapsedMs / 1000` and `simTime += elapsedMs`, does not advance `pulseIndex`, skips the 10-pulse stagnation check ([`:466`](../../packages/server/src/simulation/pulse-scheduler.ts)) and the goal-layer review ([`:529`](../../packages/server/src/simulation/pulse-scheduler.ts)), salts the rng so it does not repeat the next base pulse's draws, and stamps events with the current (next) `pulseIndex`. Base pulses may also pass `elapsedMs` (wall time since the previous pulse of any kind); undefined means `pulseIntervalMs`, today's behavior.
3. **The focused pulse runs on its own lane, gated by per-agent locks (D-73).** Base pulses run on the base lane at a fixed 6 s cadence (range 5-8; an overrun skips beats, it does not burst). A focused pulse does not queue behind the in-flight base pulse: it runs on a separate focus lane. Each agent has a lock, taken when its generate task starts and released when its commit finishes. A focused pulse for an agent whose lock is held (it is mid-call for an ambient reason) waits for that one call and then runs its own; a base pulse skips agents whose lock is held. Because tasks commit as they settle, an agent's lock is never held until the slowest call of the pulse returns. This is the design the spike measured; it is the default, not the last resort the first draft reserved it as. The first human line fires a focused pulse at once; focus ids requested during the next 300 ms coalesce into one follow-up focused pulse (D52); there is no trailing debounce. Base pulses are kept short by bounding generation (D-75) and by priority ordering in phase B (addressed first, then ambient, then fidget). The `agentStates` map is loaded once at base-pulse start ([`:244`](../../packages/server/src/simulation/pulse-scheduler.ts)) and persisted per agent, so the lanes need a single writer per agent: state is re-read under the lock and merged at commit (phase 2 work item with tests, see Consequences).
4. **`onConsult` fires when a generate task takes a slot (D-74).** `onConsult({ agentId, reason, addressed })` runs immediately before `generateIntent`, after the semaphore, so the hotel's typing bubble starts when the model call starts rather than when the task was queued.
5. **Generation has a deadline (D-75).** Each generate task is bounded by `generateDeadlineMs` (seed 20 s, kept: the spike found 8 s worse because an abandoned call is a lost turn; the per-call `LLMConfig.timeoutMs` still applies). Expiry follows the existing failure path (`llm_failure` event, `no_op`, [`:357-361`](../../packages/server/src/simulation/pulse-scheduler.ts)), so one slow model cannot hold the commit phase indefinitely.

## Rationale

- Splitting only the LLM wait out of the loop removes the sequential round trips while keeping every pure computation, every commit and every persist in the order the rest of the system assumes (single writer after commit).
- A focused pulse that ages the simulation by real elapsed time keeps emotion decay, `justActed` ([`run-engine-step.ts:104`](../../packages/engine/src/step/run-engine-step.ts)) and cooldowns honest; not advancing `pulseIndex` keeps pulse-denominated windows (hold-voice refractory 3 pulses, stagnation 40, goal review cadence) meaning what their authors intended.
- Serialization was the smallest change but it is not enough: the spike measured addressed replies at p50 7.1 s / p95 13.3 s with a queued focused pulse (c=3, 1.5 s debounce). The agent is the unit that must not run twice at once, so the lock belongs to the agent, not the pulse. Reworking the `agentStates` ownership at [`:244-253`](../../packages/server/src/simulation/pulse-scheduler.ts) is the price.
- Committing when the call settles is what releases an addressed agent's lock early; it was worth about 2 s at p95 (focus lane alone 4.3 / 11.6 s, plus commit-as-settled 4.0 / 9.6 s).
- A typing bubble starts at `onConsult`, so the reply already costs about 3.7 s of typing floor; a 1.5 s trailing debounce would spend the whole p50 slack. Hence fire on the first line and coalesce for at most 300 ms.

## Rejected Alternatives

- **Concurrent pulses without per-agent locks** — races on `agentStates`, on `lastCommittedEventId` and on `currentChannelIdByAgent`. (Concurrent pulses *with* per-agent locks are the decision above.)
- **A single in-flight pulse with a queued focused pulse** (the first draft) — measured p50 7.1 s / p95 13.3 s at c=3, 9.7 / 24.5 s at c=1; 67-90% of human lines arrive while a pulse is in flight.
- **A short base interval instead of a focused pulse** — 1-2 s pulses would ask every agent's engine step and many LLM consults to run for no reason, and do not remove head-of-line blocking.
- **Prompting the model to reply faster** — latency is the provider's, not the prompt's.
- **Advancing `pulseIndex` on focused pulses** — shortens every pulse-denominated window by the number of human lines.

## Consequences

- **Turn order is no longer guaranteed in live mode.** Tasks commit as their call settles, so events from one pulse are appended in completion order, not seeded turn order. What that changes: (1) `worldSignals` and the context window for a later-settling agent were fixed in phase A and do not see an earlier-settling agent's line (already true of the split); (2) event ids and `pulseIndex` stamping still follow append order, so replays of a live run replay the recorded order, not a reseeded one; (3) a seeded eval or replay run must use `commitOrder: "turn"` to stay byte-identical; (4) anything that assumed "agent N's commit precedes agent N+1's" (the same-pulse damper, probes grouped by turn) must read append order instead. The room speech arbiter ([ADR-0021](./0021-room-speech-arbiter.md)) compensates for the lost damper; its rule "one answer per unaddressed human line" is mandatory, not optional.
- Spike numbers (12 agents, about 3 consults per base pulse, lognormal mock model median 2.5 s / p95 6 s, 1000 addressed lines per cell), addressed reply p50 / p95: today's sequential loop 13.3 / 32.3 s; this ADR as first written (c=3, queued focused pulse, 1.5 s debounce) 7.1 / 13.3 s; focus lane, per-agent locks, commit-as-settled, c=3 **4.0 / 9.6 s**. c=1 fails (6.6 / 17.1 s); c=6 buys 0.5 s of p95 for about 5 more LLM calls/min. Base interval is flat from 4 to 8 s once the focus lane exists, so 6 s (23-25 calls/min against 29 at 4 s).
- The scheduling cannot beat the model: on a model with median 4 s / p95 10 s the best case is 5.6 / 14.1 s. D53 therefore admits a model to the hotel allowlist only after a benchmark shows p95 <= 6 s at our prompt size, and the run panel shows live LLM p95.
- LLM load rises from about 15 calls/min to 23-27 at the same consults per base pulse. It is checked against the ADR-0025 budget; busy rooms (6 consults per pulse) slip to p50 4.6 s / p95 13.2 s at c=3.
- Addressed replies should jump the gateway's 2.5 s per-room queue (FIFO ambient backlog adds about 2 s at p50).
- Per-agent locking correctness was not prototyped (the spike only gated on a lock). The real design must merge `agentStates`, `lastCommittedEventId`, `currentChannelIdByAgent` and `simTime` across lanes, and handle the addressee being mid-call for an ambient reason; it needs tests before Phase 2 exit, and the real-model numbers are re-measured then (Tilehouse `eval-plan.md` section 10).
- Events committed by focused pulses carry the next base pulse's `pulseIndex`; analyses that group by pulse see them in that pulse.
- If the spike's targets regress on the real model, the remaining levers are a faster model for addressed replies, a hedged second request, or a relaxed target, not a scheduler change.
- `SimulationRuntime.runPulse(simulationId)` ([`simulation-runtime.ts:279`](../../packages/server/src/simulation/simulation-runtime.ts)) gains the options parameter and a `getPulseIndex(simulationId)` accessor used by human ingestion ([ADR-0022](./0022-guests-and-human-ingestion.md)).

## Implementation notes (Phase 2 L3)

- `PulseSchedulerConfig` gains `pulseMode` (default `"sequential"`, the old loop, now factored into `decideAgent` / `generateFor` / `commitIntent` with identical order and output), `generateConcurrency` (3), `generateDeadlineMs` (20 000), `onConsult`, `commitOrder` (`"settle"` default, `"turn"` for eval and replay), `windowedReads`, `arbiter`, `spaceMirror`, `onAgentCommitted` and `clock`. `buildConfiguredSimulation(config, { hotel })` takes them as one `HotelSimulationOptions` bag; without it nothing changes.
- Lanes: one base pulse in flight (`inFlight`), any number of focused pulses beside it. `SimulationRuntime.runPulse(simulationId, opts?)`, `getPulseIndex`, `awaitIdle` and `resolveDeferred` are the runtime surface.
- Locks and staleness: the per-agent lock (`AgentLocks`, FIFO hand-over) is held during decide and again from the moment a generate task takes its slot until its commit ends. A base pulse skips a locked agent; a focused pulse waits for it. State is single-writer: `PulseScheduler.stateCache` is read under the lock and written by `persistAndSnapshot`, which bumps a per-agent version. A task whose agent was committed by another lane while it waited for a slot is **re-decided on fresh state** before its model call (the spike only gated on a lock). Pending tasks that no longer need a call are dropped without a call.
- `GenerateSemaphore`: with more than one slot, one is reserved; only an addressed call may take the last free slot, and waiting tasks run addressed, then ambient, then fidget (FIFO within a class). In `commitOrder: "turn"` every task is ambient so slot order equals turn order and the commit gate cannot deadlock.
- Addressed means: a `human_chat` focused pulse for that agent, or the engine's `direct_mention` / `reply_to_self` reasons. `getPriority(sim, agent, { addressed: true })` is passed only in split mode.
- `pulseIndex`: a base pulse captures its index, then increments `pulseIndex` when its decide phase ends (not when it finishes), so lines ingested and focused pulses started while it generates are stamped with the next index. A focused pulse never advances it, skips stagnation and goal review, and ages the simulation by `elapsedMs`.
- `onConsult` fires after the slot and the lock are taken, immediately before `generateIntent`. A deadline expiry is the existing `llm_failure` path.
- `PresenceProfile.responseDelayMs` is carried through `PersonaPromptProfile.responseDelayMs` and `AgentContext.responseDelayMs`; `SimulationRuntime.getResponseDelayMs` and `sampleLandingDelayMs(range, chars, rng)` give the gateway its landing delay (`min(4000, draw + 55 ms x chars)`).
- A generic `WallClockPulseLoop` (server) implements the two lanes of ADR-0024 on an injected clock; the hotel package can wrap it or keep its own.
